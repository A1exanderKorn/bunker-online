# Discord-профили и PostgreSQL

Настройка для Discord-приложения и сервера с PostgreSQL. Значения секретов не входят в Git или Docker-образ.

## Модель

- `profiles`: внутренний UUID, уникальный Discord ID (строка, не JS number), локальный ник, URL аватара Discord.
- `auth_sessions`: SHA-256 случайного токена сессии, профиль, срок 30 дней. Сам токен — только в HttpOnly cookie (Secure на HTTPS, SameSite=Lax).
- `oauth_states`: одноразовые состояния входа на 10 минут, привязанные к cookie браузера.
- `matches`: UUID отдельной партии, время начала/завершения, стартовое число игроков и режим.
- В матче также сохраняются целевой КФ и флаг случайной раздачи; в записи игрока — стартовый взвешенный КФ всей карточки.
- `match_players`: профиль, результат, номер исключения и JSONB-снимок первой раздачи, включая биологию и оба багажа.
- `schema_migrations`: версии схемы. Сервер применяет миграцию транзакционно перед началом приёма запросов.

Один аккаунт — один участник лобби, повторное подключение с другого устройства заменяет прежний сокет.
Гостевые идентификаторы находятся в отдельном пространстве имён и не могут подменить аккаунт.
Имена могут совпадать между профилями, но существующее ограничение одинаковых имён внутри лобби сохранено.
Аватар обновляется при входе через Discord. Локальный ник при повторном входе не затирается.
Смена ника влияет на следующие подключения; в уже начатой игре сохраняется прежнее имя.

В историю попадают только завершённые партии, сыгранные с авторизацией с самого старта.
Гостевые игры задним числом не импортируются. Незавершённая партия после перезапуска/сброса не считается проигрышем.
Игрок, удалённый после истечения времени реконнекта, учитывается как выбывший в общей очереди исключения.
Выбывший голосованием не получает второй номер при последующем отключении.
«Прошёл» означает оставшегося среди финальных участников, а не расчёт выживания бункера.

Завершённые матчи сначала записываются в дисковую очередь, затем одной транзакцией в БД.
При временном сбое БД запись повторяется каждые 10 секунд, в том числе после перезапуска.
Повторная запись одного UUID безопасна. Очередь — приватные данные: монтировать постоянный volume,
резервировать вместе с БД. При полном диске запись может не состояться (CRITICAL в логах).
Активные лобби по-прежнему в памяти — БД истории не восстанавливает незаконченную игру.

## Discord

В https://discord.com/developers/applications создать приложение, в OAuth2 добавить redirect URI:

`https://vbunkere.online/api/auth/discord/callback`

Для локальной разработки отдельно: `http://localhost:5173/api/auth/discord/callback`.
Нужны Client ID и Client Secret (не bot token). Секрет хранить только в локальном/VPS `.env`, не в переписке или Git.
Используется только scope `identify`; email, серверы и список друзей не запрашиваются.
Discord access/refresh token не сохраняются: access token нужен только для одного запроса профиля при входе.

## Запуск на VPS

1. Добавить настройки из `deploy/auth.env.example` в существующий `.env`, не перезаписывая его целиком.
2. Сгенерировать пароль БД: `openssl rand -hex 32` (hex не требует URL-кодирования).
3. Установить `APP_ORIGIN` точно в origin сайта, без пути. На production обязателен HTTPS.
4. Запустить штатный `bash deploy/deploy.sh`. `COMPOSE_FILE` подключает overlay с БД.
5. Проверить вход/выход через Discord, изменение ника, гостевой вход и историю завершённой партии.

БД не публикует порт на хосте. Данные в `postgres_data`, очередь в `history_outbox`.
Не применять `docker compose down -v`. Смена POSTGRES_PASSWORD в .env не меняет пароль уже созданной БД.
Перед миграцией/обновлением делать резервную копию (`pg_dump`) и проверять восстановление в отдельной БД.
Откат образа приложения НЕ откатывает миграцию схемы. Первый overlay меняет только добавочные таблицы.
Перед включением аккаунтов на публичном сервере обновить Debian и разобрать аудит npm-зависимостей.

## Локальная разработка

PostgreSQL 17 может быть локальным или отдельным тестовым контейнером. Не использовать production DATABASE_URL в тестах.
Задать `DATABASE_URL`, `APP_ORIGIN=http://localhost:5173`, Discord Client ID/Secret в окружении процесса сервера.
Для Node 22 можно загрузить свой файл командой `node --env-file=.env server/dist/server/index.js` из корня
после `npm --prefix server run build`. `.env` не загружается автоматически через npm dev.
Фронтенд запускается обычным `npm --prefix frontend run dev`: `/api` и `/socket.io` проксируются на порт 3000.
Без DATABASE_URL игра работает гостевой, профиль показывает, что вход пока не настроен.
Если БД настроена, но недоступна при старте, сервер отказывается стартовать вместо потери истории.

## API

- `GET /api/auth/session`: пользователь или null, доступность входа.
- `GET /api/auth/discord`, `GET /api/auth/discord/callback`: вход и callback.
- `POST /api/auth/logout`: удаление серверной сессии и отключение её сокетов.
- `GET /api/profile`, `PATCH /api/profile` (`{nickname}`): только свой профиль.
- `GET /api/profile/matches?offset=0`: по 20 матчей, без характеристик.
- `GET /api/profile/matches/:id`: только собственная запись со стартовыми характеристиками.

Изменяющие запросы требуют Origin=APP_ORIGIN и заголовок `X-Profile-Request: 1`.
API не кешируется. История не раскрывается другим пользователям, гостям или через публичный ID матча.
